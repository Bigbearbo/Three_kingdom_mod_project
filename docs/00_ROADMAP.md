# 路線圖與實驗驗收（v0.1）

## 設計取向

- 保留原版好用的戰場系統；玩家可以大量手操，但不應為了避免被雜將自動戰鬥打敗而被迫每場手操。
- 名將不只技能／機體強，也要能帶更多兵；弱將在小戰場弱勢，但數量與調度仍有用。
- 不追求所有武將強度均等；追求各種資源（名將、兵力、錢、時間、城池）之間的清楚取捨。
- 軍費著重「平時養兵可持續；戰爭造成傷亡要付代價」；避免低維持費無意間令後期軍團數翻倍。
- 要同時檢查 AI 與手動／自動戰鬥，不能只用一兩次王牌軍團勝利判定平衡。

## P0：資料來源與工具基線（優先執行）

1. 記錄安裝來源、版本號、DLC、遊戲難度、單位規模設定、載入順序、已訂閱 Mod。建立無 Mod 的新存檔基準。
2. 用 RPFM 唯讀開啟原版 Pack，核對單位人數資料表、招募限制、維持費／招募費與補員相關參照。
3. 開啟要參考的既有 Mod，建立衝突表：資料表＋key、整檔覆寫、腳本事件、startpos、是否 DLL。
4. 在乾淨環境做一個**不改玩法**的最小 `.pack`；證明能載入、解除安裝、回復原版。記錄畫面或日誌。

**P0 結果**：一份帶出處的可行性報告；哪些功能是原生資料表、Lua、DLL、仍未知。不能只靠網路文章推定。

## P1：帶兵量差異（第一個玩法原型）

1. 選一種步兵與一種騎兵做三級單位大小版本；沿用原版兵種特性，不偷改兵種剋制與攻速。
2. 實作普通／優秀／名將可招募版本的**可驗證規則**。先以等級或明確特性解鎖；再評估是否可依複合「統兵」數值判定。
3. 驗證實際人數、UI、招募費／維持費比例、戰場實例、補員、既有兵的替換、AI 招募與自動戰鬥。拒絕只看 DB 欄位當完成。
4. 如果限制規則原生做不到，記錄具體缺口，再考慮 Lua 或 Script Extender。

**退出條件**：玩家與 AI 都能在 2 個不同派系招到正確兵額，至少 10 場重複戰鬥沒有崩潰或違反規則。

## P2：軍費與補員

優先試行 `0.5 × 原本維持費`。對補充的人數額外計費，例如 `招募價 × 補充人數／原編制上限`。

必須先做「實際觀察遊戲回合結算時間線」，找出能區分原版補員與換將／合併／招募的唯一身份或事件。玩家破產時的扣款與負值處理必須核對原生行為；**不能直接假設自訂腳本扣錢會和原本軍費完全一樣觸發破產**。

驗收：滿員、戰後半殘、逐回合補員、部隊合併、招募新兵、解散再招、破產邊界、被圍城／缺糧、AI 與玩家皆不出現漏洞。

## P3：AI 調整與穩定性

驗證電腦是否會招募大／小版本、偏好合適的統兵武將、維持財政、分配補員優先權；不得只加強玩家。保持難度加成為獨立參數，不把 AI 補償當成所有難度通用值。

## P4：實戰調整

至少設置 190／200 兩個開局（須有相應 DLC），每一測試維持固定遊戲版本、載入順序、難度、單位規模、種子（若能控制）和參戰條件。用 `docs/03_TEST_MATRIX.md` 記錄對照，重點觀察王牌軍團出場率、其他軍團存在價值、軍隊平均維持量、總軍費、補員費、自動／手動結果偏差。

## P5：獨立開局包

若核心規則通過驗收，才為 190／194／200 年等原有開局製作獨立 `startpos` 或事件包。不要在同一個核心 Pack 內硬捆多個劇本的 startpos。

## P6：延期研究

城池獨立士兵庫、武將從駐軍中領兵、長期關押俘虜與招降、永久降低兵額上限、夜襲援軍延遲，需先對照可用腳本 API 與 UI 限制；此階段不列作 v0.1 承諾。

## 工作方式

每次改動只解決一個可驗證的問題。保留原始來源、變更明細、對照組、通過與失敗測試。發布前同時提供乾淨版的相容性說明。
